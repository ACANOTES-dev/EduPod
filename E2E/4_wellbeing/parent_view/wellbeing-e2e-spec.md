# Wellbeing — E2E Test Specification (Parent)

> **Generated:** 2026-04-21
> **Module slug:** `wellbeing`
> **Perspective:** Parent tier — role_key `parent`, role_tier `parent`. A parent user is scoped to their **own linked children** (rows in `student_parents`). Parents have **NO access** to the wellbeing, behaviour, pastoral, safeguarding, early-warnings, or staff-wellbeing hubs — those routes must 403 or redirect. Parents DO have a dedicated **Parent Portal** under `/behaviour/parent-portal` plus a recognition wall, appeal submission, acknowledgement flow, and a parent self-referral path into pastoral care. >   **Pages covered:** 2 parent-facing wellbeing pages (`/behaviour/parent-portal`, `/behaviour/parent-portal/recognition`) + inbox surfaces + the parent dashboard home, plus ~15 negative-URL probes covering every staff-facing wellbeing route.
>   **Base URL:** `https://nhqs.edupod.app`

## How to use this spec

Every row is one observable check. Mark **Pass / Fail / Blocked** in the rightmost column. A `Fail` on any row where severity is unspecified is a release blocker. Rows explicitly labelled `(info)` are diagnostic and do not block release. Rows marked `[POS]` are positive assertions ("parent CAN do X"); rows marked `[NEG]` are negative assertions ("parent CANNOT do X"). Negative assertions are load-bearing — a `Fail` on any `[NEG]` row is always a release blocker.

Run this spec top-to-bottom in a fresh browser session per locale (once in `/en/*`, once in `/ar/*`). Keep DevTools open with **Network** and **Console** tabs visible — both are asserted on.

The parent spec is single-session (no dual-control), but it relies on a second browser profile signed in as an admin to toggle guardian restrictions at §12 and to generate amendments at §7.

## 2. Out of scope for this spec

This spec exercises **only** the UI-visible surface that a parent-role user can reach, plus the negative matrix they must be blocked from. It does **NOT** cover:

- **Admin flows** — `../admin_view/wellbeing-e2e-spec.md` (all 79 pages, dual-control, finalisation, settings, platform admin).
- **Teacher flows** — `../teacher_view/wellbeing-e2e-spec.md` (teacher-scoped incident logging, pastoral recording, restricted pastoral tier access, etc.).
- **Student flows** — `../student_view/wellbeing-e2e-spec.md` (student self-service acknowledgements, student voice submissions, check-in responses).
- **Cross-tenant RLS matrix** across all 54 tenant-scoped wellbeing tables — `../integration/wellbeing-integration-spec.md` (this spec does one UI-visible probe in §18; the integration spec does the full matrix).
- **Contract edges** — every Zod boundary, every permission-denial variant per endpoint — `../integration/wellbeing-integration-spec.md`.
- **BullMQ job chains** (incident → acknowledgement enqueue → email/SMS dispatch → delivery receipt projection) — `../worker/wellbeing-worker-spec.md`. This spec asserts that the parent sees the downstream inbox notification but does not trace the worker chain.
- **Perf / latency budgets for parent endpoints** — `../perf/wellbeing-perf-spec.md`.
- **OWASP + full permission matrix × all roles** — `../security/wellbeing-security-spec.md`.
- **PDF byte-level correctness** for exclusion notices / appeal decision letters the parent downloads — content-type + download-completes only here; bytes in integration spec.
- **Browser matrix beyond desktop Chrome + 375px iPhone SE emulation.**
- **Accessibility audits** — structural checks only (`alt`, keyboard focus, aria-labels). Run axe-core / Lighthouse separately.
- **Visual regression** — no pixel diffs.
- **Arabic name / RTL-text-shaping edge cases** — structural RTL assertion only in §16.

## 20. Observations spotted during the walkthrough

Log anything the tester notices that is not a hard Fail but warrants follow-up. Seed list (populate during execution):

- **P-1** — Error banner on `/behaviour/parent-portal`: current build catches summary errors and silently renders an empty state (`behaviour-parent.service.ts` + page.tsx swallow errors to empty arrays). Parents deserve a visible "We couldn't load your data — retry" banner with a retry button, analogous to the admin wellbeing dashboard's `wellbeing.dashboard.error` + `wellbeing.dashboard.retry` pattern. Consider wiring the same copy.
- **P-2** — Appeal submission entry point: the parent portal currently lists sanctions in read-only mode with no visible "Submit appeal" CTA. Parents can only reach `POST /v1/parent/behaviour/appeal` if they already know the endpoint exists. Recommend adding an inline Appeal action on eligible sanction rows (status=`scheduled`) with a small lightweight form OR a separate `/behaviour/parent-portal/appeals/new?sanctionId=…` page.
- **P-3** — Publication-approval surface for own children's awards: the `/behaviour/parent-portal/recognition` page does not currently surface pending-consent awards for parent approval. Approvals are processed via inbox email link only. Recommend a dedicated "Pending your approval" banner at the top of the recognition page listing own-child items with inline Approve/Decline actions.
- **P-4** — Self-referral CTA: "Report a concern" is not currently surfaced from the parent portal or parent dashboard. Parents can only reach `POST /v1/parent/pastoral/self-referral` if they know the endpoint exists. Recommend a prominent CTA on `/dashboard/parent` Overview tab + on `/behaviour/parent-portal`.
- **P-5** — Guardian restriction transparency: current restriction logic returns empty arrays (per `behaviour-parent.service.ts:76-86`, `:177-178`, `:361-363`) but does not tell the parent WHY their data is empty. A friendly explanatory banner ("This record has been restricted. Contact the school to learn more.") is strongly recommended so parents do not think the system is broken.
- **P-6** — Amendment diff: the parent-portal re-acknowledgement flow shows only the NEW narrative (post-correction). This is correct for privacy but parents would benefit from a subtle "Updated from previous version" marker. Consider a light badge without exposing the staff-side diff.
- **P-7** — Parent-portal Documents tab: no dedicated tab exists. Documents surface only via inbox. Consider a Documents tab listing `documents.target_audience IN ('parent','parent_student')` scoped to the active child, to give parents a durable archive separate from inbox retention windows.
- **P-8** — Sibling isolation: `GET /v1/parent/behaviour/summary` always returns exactly the linked children. Verified by `behaviour-parent.service.ts:58-63`. Cross-tenant + sibling isolation both covered by the service-layer `verifyParentStudentLink` + RLS. Defence-in-depth working as designed.
