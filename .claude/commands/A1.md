# Wellbeing Walkthrough — Execute Session $ARGUMENTS

You are executing **Session $ARGUMENTS** of the Wellbeing Module ship-gate Playwright walkthrough. This is a ten-session end-to-end review of the wellbeing module (behaviour, pastoral care, safeguarding, early warnings, staff wellbeing). The final deliverable is a ship-ready report that the user audits once — if they agree with the recommendation, the module ships without further review.

`$ARGUMENTS` is the session ID — `S0`, `S1`, …, `S9` (case-insensitive).

## Step 0 · Read the context

Before doing anything else, read these three files in order:

1. **`E2E/4_wellbeing/new-e2e-testing/PLAN.md`** — master plan: operating principles (trust but verify, no silent fixes, screenshots permitted but deleted, reproducibility, blast-radius awareness), accounts to use, standard per-page checklist (§4), issue format (§6), severity guide, exit criteria (§7), execution rules (§8).
2. **`E2E/4_wellbeing/new-e2e-testing/$ARGUMENTS_*.md`** — this session's blueprint (find by matching the `$ARGUMENTS` prefix case-insensitively; e.g. `$ARGUMENTS=S0` matches `S0_seeding_scope_map.md`, `$ARGUMENTS=s1` matches `S1_behaviour_A.md`). Scope, routes, flows, exit criteria.
3. **`E2E/4_wellbeing/new-e2e-testing/PLAYWRIGHT_LOG.md`** — current state of the log. Confirm all prior sessions are marked Complete. Confirm the session ledger row for $ARGUMENTS is either `Not started` or `In progress` (resuming).

Do not skim. PLAN.md is the source of truth for conventions; the blueprint is the source of truth for what this session does; the log is the source of truth for what's already been found and fixed.

## Step 1 · Validate prerequisites

From the blueprint's "Prerequisites" section, verify each prerequisite is true. In particular:

- The prior session is marked **Complete** in the PLAYWRIGHT_LOG.md session ledger, with no unresolved P0/P1/P2 issues open.
- NHQS is reachable at `https://nhqs.edupod.app` and admin login works (`owner@nhqs.test` / `Password123!` — see PLAN.md §5 for full account list).
- If the blueprint expects seeded data (S1+ all do), run a quick DB or list-view count to confirm the data is present.

If any prerequisite fails, STOP. Tell the user what's missing and do not proceed.

**Exception for S0** — S0 has no prior-session prerequisite; it sets up the dataset for everything that follows.

## Step 2 · Execute the session blueprint

Walk every route listed in the blueprint's §2 scope. For each page:

- Apply PLAN.md §4 (standard checklist) — visual, functional, i18n, role, network.
- Apply any page-specific or session-specific checks the blueprint adds on top.
- Follow prescribed user flows end-to-end (e.g. S1's five UI-driven incidents, S4's self-referral round-trip, S5's break-glass flow).
- Tick the route's box in `_scope-map.md` as you finish it.

Use the Playwright MCP tools. Prefer `browser_snapshot` for structure / presence / text checks. Use `browser_take_screenshot` only when pixel-level fidelity is the specific concern (spacing, overlap, bottom-margin cut-offs, RTL visual glitches) — and delete those screenshots before session close.

## Step 3 · Log every issue before fixing it

For every issue found (visual, functional, data, permission, copy, anything):

1. Write the entry to `PLAYWRIGHT_LOG.md` under the session's `## $ARGUMENTS — ...` heading in the format from PLAN.md §6:

   ```
   ### W-$ARGUMENTS-NNN — {short title}
   - **Severity:** P0 | P1 | P2 | P3
   - **Route:** /en/...
   - **Role:** {email}
   - **Viewport:** 1440x900 | 375x667 | RTL
   - **Steps:** 1. ... 2. ... 3. ...
   - **Expected:** ...
   - **Actual:** ...
   - **Evidence:** (screenshot reference if any — deleted before session close)
   - **Fix:** {pending}
   - **Verified:** {pending}
   ```

2. Number entries sequentially within the session: `W-$ARGUMENTS-001`, `W-$ARGUMENTS-002`, …

3. Do this **before** attempting the fix. No silent fixes — the log must show the bug was found, not just that it was fixed.

## Step 4 · Fix, deploy, verify

For every P0, P1, and P2 issue logged:

1. Implement the fix in code. Follow repo conventions (`CLAUDE.md`, `.claude/rules/*.md`). Respect blast radius — consult `docs/architecture/module-blast-radius.md`, `danger-zones.md`, `state-machines.md`, `event-job-catalog.md` as appropriate.
2. Commit locally with a conventional-commits message (`fix(wellbeing): …` etc.).
3. Run regression tests per `CLAUDE.md` — `turbo test` or the relevant scoped command for the affected packages.
4. Deploy to production via rsync + SSH per `feedback_deploy_workflow.md`. **Never `git push` to deploy.** Exclude `.git`, `node_modules`, `.next`, `dist`, `.env`, `.env.local`, `.turbo`, `*.tsbuildinfo`. `chown -R edupod:edupod /opt/edupod/app/` after rsync; verify `.env` symlinks.
5. Re-walk the reproduction steps on production. If the issue is gone, update the log entry:
   - **Fix:** {commit SHA} — {one-line summary}
   - **Verified:** {YYYY-MM-DD} — re-walked, passes.
6. If the fix touches architecture (cross-module dependency, new/changed BullMQ job, state machine change, non-obvious coupling, new module), update the relevant file in `docs/architecture/` in the same commit per `.claude/rules/architecture-policing.md`.

P3 issues may be batched into one polish commit at the end of the session (or deferred with a written reason if it's truly cosmetic-only).

## Step 5 · Close the session

Only proceed when every P0/P1/P2 in the session's issue list is marked **Verified:** or **Deferred:** (deferrals must have a written reason).

1. Confirm every route owned by this session has its box ticked in `_scope-map.md`.
2. Delete every screenshot created during the session. Sweep: `find E2E/4_wellbeing/new-e2e-testing -name '*.png' -o -name '*.jpg' -o -name '*.jpeg'` — expected output: empty.
3. Append the session summary paragraph under the `## $ARGUMENTS — ...` heading in `PLAYWRIGHT_LOG.md`. 2–4 sentences: what was walked, what was found, what was fixed, any deferrals with reason, standout concerns to carry forward.
4. Update the session ledger row at the top of `PLAYWRIGHT_LOG.md`:
   - Started: YYYY-MM-DD (date this session began)
   - Completed: YYYY-MM-DD
   - Issues opened: total count
   - P0 / P1 / P2 / P3: per-severity counts
   - Status: **Complete**
5. Commit everything with a message like `docs(wellbeing-walkthrough): complete $ARGUMENTS — {N} issues logged, {N} fixed, {N} deferred`.

## Rules

- **Sequential only.** Do not start, peek at, or read the plan for any session beyond $ARGUMENTS. If the user wants the next one, they'll invoke `/A1` again with the next session ID.
- **Impartial.** Do not read `E2E/4_wellbeing/BUG-LOG.md`, `DECISIONS.md`, `RESOLUTION-PLAN.md`, `PLAYWRIGHT-WALKTHROUGH-RESULTS.md`, or any other artefact from the prior walkthrough. This review is independent — the user will compare the two outputs themselves.
- **Autonomous.** Server access, DB seeding (S0), production fixes/deploys, and architecture-doc updates are pre-approved. Do not ask for approval during execution. Stop and ask only if:
  - Scope would genuinely expand beyond $ARGUMENTS' stated scope in the blueprint
  - A change requires touching a production DB column / table that is NOT operational maintenance (dropping data, altering schema beyond an agreed migration)
  - A prerequisite that should be true is false and you can't safely proceed
- **Never skip the fix-and-verify loop.** A session is not Complete until every P0/P1/P2 it logged is Verified or Deferred.
- **No screenshots lingering.** Delete every PNG / JPG in the walkthrough folder before session close.
- **Tenant URLs.** NHQS lives at `nhqs.edupod.app` or `edupod.app` — never `nurul-huda.edupod.app`.
